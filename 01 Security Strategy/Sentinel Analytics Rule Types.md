# Sentinel Analytics Rule Types

## Purpose

Choose which [[Microsoft Sentinel]] analytics rule type, or which single-instance template, turns a detection need into alerts and incidents.

---

## Why Architects Choose It

- Each rule type answers a different detection question: **correlation** (Fusion), **another product's alerts** (Microsoft Security), **behavioural baseline** (Anomaly), **custom KQL** (Scheduled/NRT), or **known-bad indicators** (Threat Intelligence).
- Picking the wrong type gives you duplicate incidents, missed multistage attacks, or alert noise.
- The type also decides **whether you can customize it**. Fusion, ML Behavior Analytics and TI matching analytics are **one-instance, not customizable** rules.
- In the **unified Defender portal**, two of these rule types are **switched off** and [[Microsoft Defender XDR]] takes over their job. That's an architecture decision, not a setting.

---

## The Rule Types

| Rule type | What it does | Customizable? | Exam trigger |
| --- | --- | --- | --- |
| **Scheduled** | KQL query on an interval over a lookback window. Raises an alert when the result passes a threshold. Most common type. | Fully | "custom query", "specific condition", "every X hours" |
| **Near-real-time (NRT)** | Limited subset of Scheduled. Runs **every minute**. | Mostly (some limits) | "as close to real time as possible", "immediate response" |
| **Microsoft Security** (incident creation) | Creates Sentinel **incidents** in real time from **alerts produced by other Microsoft security products** (Defender for Cloud Apps, Defender for Cloud, Entra ID Protection, etc.) | Filter by product/severity/name | "process alerts generated by Defender for…", "events from other security platforms" |
| **Anomaly** | ML builds a **behavioural baseline** over time and flags deviations. Results go to the **`Anomalies` table**, not straight to alerts. Built-ins can't be edited: duplicate one, test it in **Flighting** mode, then move it to Production. | Duplicate and tune | "out of the ordinary", "user logging in after hours", "unusual for this user" |
| **Fusion** (Advanced multistage attack detection) | ML correlation engine that combines **many low-fidelity alerts and events across products** into high-fidelity incidents. **Enabled by default.** Only one rule. | No (hidden logic) | "correlate low-impact events", "exploit chaining", "multistage attack", "individually not suspicious" |
| **Threat Intelligence** (Microsoft TI matching analytics) | Matches CEF, Syslog and DNS logs against Microsoft TI domain/IP/URL indicators | No | "match against Microsoft threat indicators" (see [[Threat Intelligence Management in Sentinel]]) |
| **ML Behavior Analytics** | Microsoft ML rules for **anomalous SSH and RDP logins** (IP, geolocation, user history) | No (preview) | "anomalous RDP/SSH login" |

---

## When to Use

- **Fusion**: lots of noisy, low-severity signals from many products, where the attack only shows up when they're chained together.
- **Microsoft Security**: Sentinel-only deployments (not using Defender XDR incident integration) that need incidents from Defender product alerts.
- **Anomaly**: insider-style or unusual behaviour with no known signature (time, volume, location deviations).
- **Scheduled**: your own detection logic for any ingested source, including non-Microsoft ones.
- **NRT**: high-impact events where minutes matter (e.g. break-glass account sign-in).

## When NOT to Use

- **Microsoft Security rules** once **Defender XDR incident integration** is on or Sentinel is **onboarded to the Defender portal**. They aren't available and existing ones are auto-disabled, because XDR creates those incidents.
- **Fusion** in the same situations (Defender portal / XDR integration). The XDR correlation engine replaces it.
- **NRT** for heavy queries or long lookbacks. Use Scheduled.
- **Anomaly** when you need an alert straight away. Anomalies are **context** (hunting, enrichment), not alerts on their own.
- **Scheduled rules over Defender product alerts** to make incidents. That creates duplicates; use Microsoft Security rules (Sentinel-only) or XDR integration.

## Architecture Decisions

```
What do you need to detect?
  ↓
Many weak signals that only matter TOGETHER (exploit chaining, multistage)?
  → Fusion (Advanced multistage attack detection)

Alerts ALREADY raised by another Microsoft security product (Defender for Cloud Apps, etc.)?
  → Microsoft Security rule (incident creation)
     … but if Sentinel is in the Defender portal / XDR integration is on → XDR creates them

Behaviour that's unusual for THIS user/entity (after hours, odd volume)?
  → Anomaly rule (ML baseline → Anomalies table)
     Anomalous RDP/SSH logins specifically → ML Behavior Analytics

Your own logic over any data source?
  ├─ Minutes matter  → NRT (runs every minute)
  └─ Otherwise       → Scheduled (interval + lookback + threshold)

Logs vs. Microsoft's known-bad indicators?
  → Microsoft Threat Intelligence matching analytics
```

**Three-word recall:** *Correlate → Fusion. Ingest-alerts → Microsoft Security. Unusual → Anomaly.*

## Exam Scenario (got wrong)

> Azure + M365. Defender for Cloud Apps protects a multicloud estate. Sentinel ingests Azure and non-Azure logs. Track (1) innocuous events that may indicate exploit chaining, (2) events from other security platforms such as Defender, (3) other suspicious behaviour. Pick a rule template for each.

| Situation | Answer | Why |
| --- | --- | --- |
| Correlate **low-impact events and alerts** | **Fusion** | "Low-impact" + "correlate" + "exploit chaining" = Fusion's definition: many low-fidelity signals combined into one high-fidelity incident. |
| Process **alerts generated by Defender for Cloud Apps** | **Microsoft Security** | Alerts already exist in another Microsoft product. This rule type turns them into Sentinel incidents. |
| Detect a user **logging in after hours** | **Anomaly** ✅ | Deviation from a learned baseline of that user's behaviour. |
| (Distractor) NRT | ❌ | NRT is about **speed** (every minute), not correlation, other products' alerts, or baselines. |

**Trap:** "low-impact" sounds like it doesn't need anything special, but low-impact signals are exactly what **Fusion** exists for. And "Defender for Cloud Apps alerts" tempts you toward a Scheduled/NRT query, when the type built for ingesting other products' alerts is **Microsoft Security**.

## Comparison

| Compare | Difference |
| --- | --- |
| **Fusion vs. Anomaly** | Fusion correlates **multiple alerts/events across products** into an incident. Anomaly baselines **one behaviour** and writes deviations to a table. |
| **Fusion vs. Defender XDR correlation** | Same job (multistage correlation). In the Defender portal, **XDR's engine replaces Fusion**. |
| **Microsoft Security rule vs. Defender XDR incident integration** | Sentinel creates incidents from product alerts vs. XDR creates and syncs incidents. Enabling XDR integration **disables** Microsoft Security rules. |
| **Scheduled vs. NRT** | Interval + lookback (up to days) vs. every minute with limitations. |
| **Anomaly rule vs. UEBA** | Anomaly rules run ML templates that write to `Anomalies`. UEBA builds entity profiles and behaviour analytics (`BehaviorAnalytics` table) for investigation. Both are baseline-based. |
| **Anomaly vs. ML Behavior Analytics** | Customizable anomaly templates (many behaviours) vs. fixed Microsoft rules for **RDP/SSH** login anomalies. |
| **Analytics rule vs. automation rule** | Detection (creates alerts/incidents) vs. response/triage on incidents. See [[Playbooks and Automation Rules]]. |
| **Analytics rule vs. custom detection (Defender)** | Sentinel analytics rule vs. Defender XDR custom detection. Microsoft now recommends **custom detections** for new rules in the unified platform. |

## What's New in SC-100

- Matching **rule type → detection requirement** as a design decision.
- **Unified platform effect**: Fusion and Microsoft Security rules are disabled once Sentinel is in the Defender portal (mandatory after **31 Mar 2027**) or XDR integration is on, and XDR correlation takes over.
- Positioning **custom detections** (Defender) as the go-forward way to author new rules.

## Exam Tips

- **"Low-impact", "exploit chaining", "multistage", "correlate across products" → Fusion.**
- **"Alerts from Defender for Cloud Apps / Defender for Cloud / Entra ID Protection" → Microsoft Security rule.**
- **"After hours", "unusual for this user", "baseline" → Anomaly.**
- **"Every minute", "as close to real time as possible" → NRT.**
- Old practice questions assume the **Azure portal** Sentinel, where Fusion and Microsoft Security rules still exist. Answer the question as written.

## Common Exam Confusion

- **NRT vs. Fusion**: real-time **speed** vs. multi-signal **correlation**.
- **Anomaly vs. Fusion**: both use ML. One baselines behaviour, the other chains alerts.
- **Microsoft Security rule vs. a data connector**: the connector **ingests** alerts, but they don't become incidents until a Microsoft Security rule (or XDR integration) creates them.
